# Training with PolyBot v2

PolyBot uses one typed `TrainingConfig` in the GUI, CLI, and saved model metadata. Choose PPO, DQN, or TQC explicitly in the CLI. In the GUI, each algorithm has its own parameter panel; the other panels are hidden. Select a preset first, then expose advanced settings if needed. Saving a configuration writes the exact resolved JSON accepted by `polybot-train --config path.json`.

## The three learners

PPO is **on-policy**: it collects a fresh rollout, updates on it for several epochs, and discards that rollout. Its action is `Box(2)` with continuous steering in `[-1, 1]` and signed longitudinal demand in `[-1, 1]` (positive throttle, negative brake). PPO and TQC share this action schema and the same low-level digital pulse adapter. A fresh policy can receive a modest forward mean bias; learning can override it. An optional fixed PPO teacher and continuous ghost-action imitation remain available.

For teacher transfer, `teacher_student --stage pretrain --tqc-actor-init` copies the TQC actor exactly into a PPO policy. By default it uses a frozen TQC base with a trainable residual (`tqc_residual`). Add `--student-architecture tqc_compatible` to initialize the full TQC-compatible actor as trainable PPO; this supports fresh PPO rollout sizes such as 4,096 steps while retaining the exact teacher action at initialization. PPO rollout length cannot be changed when resuming a checkpoint, so choose it before the first PPO update. Validate the graft with five deterministic full laps before fine-tuning.

DQN in the UI now uses **QR-DQN** from SB3 Contrib. It is off-policy: it stores experiences in replay and predicts a distribution of future returns per native digital action. It chooses by mean predicted return, with epsilon exploration. `dqn.n_quantiles` defaults to 32. Curriculum phases reheat epsilon and decay it across the phase using the existing DQN exploration settings; evaluation and checkpoint saves do not restart the schedule. Replay, network weights, target network, and optimizer stay intact between phases. It has no actor network, teacher, or forward guard. **DQN does not use PWM**: it holds exactly the selected keys throughout `frame_skip` physics ticks. Its default action schema is `digital-discrete-9-v2`:

| Index | Steering | Pedal |
| ---: | --- | --- |
| 0 | straight | coast |
| 1 | straight | throttle |
| 2 | straight | brake |
| 3 | left | coast |
| 4 | left | throttle |
| 5 | left | brake |
| 6 | right | coast |
| 7 | right | throttle |
| 8 | right | brake |

Set `dqn.action_set` to `no_brake` (CLI: `--dqn-action-set no_brake`) for a six-action first stage: straight/left/right, each with coast or throttle. This has its own `digital-discrete-6-no-brake-v2` schema and cannot be resumed as a nine-action model directly. `expand_no_brake_checkpoint` copies the six learned Q outputs into the corresponding nine-action outputs, initializes brake outputs below coast, remaps replay actions, and writes a resumable nine-action checkpoint. `tools/start_staged_dqn.py` runs a fresh six-action Summer 1 model in the GUI and automatically performs this transfer after a deterministic evaluation reaches 15% progress (no earlier than 100,000 steps), or at 600,000 steps at the latest. The second stage uses the remaining budget up to two million total steps. A user-requested early stop does not trigger transfer.

Existing vanilla DQN checkpoints remain available for evaluation and driving. They cannot resume directly under QR-DQN. `migrate_dqn_to_qr` copies their hidden layers, repeats each old Q-value across the new quantile outputs so initial greedy decisions match, preserves replay and step count, and writes a separate resumable QR-DQN checkpoint. The optimizer starts fresh after migration.

TQC is **off-policy**: it reuses past decisions from a replay buffer. Its `Box(2)` action contains steering in [-1, 1] and signed longitudinal demand in [-1, 1]. Positive longitudinal demand means throttle duty; negative means brake duty. Deterministic pulse scheduling turns that demand into digital physics-tick actions. The learner's replay action is the exact continuous action executed through this adapter. TQC uses automatic entropy tuning and a seeded, forward-biased replay warmup until `learning_starts`. The mature policy has no forward guard, actor recovery snapshot, rehearsal, or track-specific rule.

The `tiny`, `compact`, and `standard` architecture choices use two hidden layers of 64, 128, or 256 units. DQN also offers `yosh_2020` with 64 then 16 hidden units, matching the architecture [Yosh published for an earlier Trackmania model](https://www.youtube.com/watch?v=_oNK08LvZ-g); it is not a verified specification for his later DQN. PolyBot's observation inputs differ. The GUI shows actual network and total parameter counts when training starts. For DQN, metadata records `actor_parameters=0` and puts the Q-network count in `critic_parameters`; the GUI calls it a Q-network. PPO often has higher decisions per second; replay-based DQN and TQC can reuse experiences. Hardware, architecture, and update frequency determine speed.

## What a training step means

One environment step is one policy decision. `frame_skip` is the number of fixed physics ticks for that decision. PPO/TQC may schedule different digital pulses within it; DQN holds one digital control unchanged. If the simulator limits packet length, PolyBot splits that hold into identical smaller packets. Increasing frame skip often improves throughput but leaves the policy less time to correct a mistake. TPS is environment steps per wall-clock second, including neural-network updates and simulator communication.

`timesteps` is the **total** planned budget across curriculum phases. Full track and fixed/timed sections use one phase; sequential quarters uses five phases (Q1–Q4 and full); Q4 then full uses two. Section starts spawn 5% of track length before the target by default: Q2 spawns at 20% and learns 25–50%; Q3 spawns at 45% and learns 50–75%; Q4 spawns at 70% and learns 75–100%. Q1 clamps to zero. The reference replays only to the spawn point. Random quarters uses the same lead-in for its seeded target quarter. Custom section phases may set `lead_in_ratio`. Full-track deterministic evaluation remains separate from section training, and only it can replace champion. The GUI's Curriculum tab shows each spawn point and target end; CLI users can pass `--curriculum custom --custom-phases phases.json` or a full v2 config file. The section completion bonus occurs only at the target end.

The PolyTrack worker computes initial curriculum velocity and angular velocity from recent replayed car states while still returning `ticks_advanced=0`. It carries through the final replay control as `previous_action`, so the first policy observation, steering and action-change reward match the handoff. GUI status shows the absolute lap position, section-relative progress, lead-in/target stage, and one reset diagnostic per phase. A checkpoint saved with `dqn.action_set=no_brake` resumes with that same action set; the GUI selects it from checkpoint metadata and schema validation rejects a mismatch.

## Rewards

Choose **Balanced**, **Learning**, or **Pace** without editing 69 numbers. Existing named track profiles remain available. The Rewards tab offers six simple controls and shows their affected parameters; Advanced reveals every numerical coefficient with an explanation of its unit and effect. Save, duplicate, reset, or compare profiles. The exact resolved values are serialized with every model. Training never silently changes them.

The reward system calculates named components for Progress, Guidance, Driving quality, Airborne behaviour, Milestones, and Failure. Each step logs every raw term plus category totals; the totals must sum to the raw reward. All three algorithms use normalized `ControlDemand` for reward accounting. For example, continuous brake duty 0.05 incurs 5% of a per-second ground-brake penalty; native digital DQN brake is full duty. The `reward_scale` multiplies the score sent to the learner, while event diagnostics retain raw points. DQN and TQC store those rewards in replay, so changing reward definitions mid-run would leave stale values and is rejected on resume.

The reference ghost defines route progress and lookahead. Optional ghost guidance rewards are separately controlled by the profile. A high reward for touching a barrier or a false landing penalty can teach the wrong driving line; inspect the per-term diagnostics and deterministic evaluation before deciding a profile helps.

For Summer 1 pace polishing, air braking is applied only while **all four wheels are off the ground**. `airborne_brake_bonus_per_s` is multiplied by executed brake duty and elapsed physics time; it is 2.0 in the Summer 1 20s pace profile. When any wheel touches, the overlay immediately returns to the base policy action and only the ground-brake penalty applies. The normal TQC actor chooses its controls; an optional WR-search air-brake overlay can hold a selected brake duty inside a detected airborne region. Because continuous controls are pulse-density scheduled, duty `0.02` produces roughly one brake tick per 50 ticks (tapping), while duty `1.0` holds brake continuously. Evaluation's `air_brake_time_s` is duty-weighted brake time, not time spent with any brake pulse. Episode summaries also record active control windows, pulse events, average and maximum duty, and 5%-of-track usage windows. The updated applied-control reward semantics are versioned in TQC metadata, so an old TQC replay must be refilled from the proven policy before learning with the new reward.

## Evaluation and models

At `evaluation.interval_steps`, the runner releases the training simulator and drives a frozen policy deterministically on full-track seeded episodes. It reports finish rate, median/mean progress, best and median finished lap, and crash/off-track/stall rates. Champion ranking uses those results. The latest policy can regress without replacing champion. **Continue best model** resumes whichever saved evaluation ranks higher and, after each weaker evaluation, restores the champion and its replay before more training. An older champion without replay reuses the current run's replay on rollback. A stochastic training finish alone never promotes a champion.

**Pace polishing** is an advanced TQC continuation mode for the evaluated champion specifically. Its Summer 1 preset runs 25,000 steps by default (the GUI also offers 50,000), evaluates five full laps after the first 1,000 decisions and then every 5,000 steps, and uses a compact actor, LR `1e-5`, batch 256, replay capacity 250,000, `gamma=0.995`, `tau=0.005`, one gradient step per four decisions, `auto_0.1` entropy, a `1e-5` action drift cap, and a 0.15s lap tolerance. A severe regression restores champion and ends the polish block. Live tests showed that even this small action cap can cross a PWM/physics threshold, so full-lap evaluation remains the acceptance criterion. TQC resume applies the new rate to actor, critic, and entropy optimizer groups immediately. The anchor uses champion-path and replay observations and is renewed after a confirmed faster champion. Deterministic search remains a separate tool: it probes actor output and tapered progress-window biases, screens one lap, confirms a faster candidate over the configured full evaluation, then atomically promotes its staged checkpoint. `pace-history.jsonl` records only accepted champions.

**Tuned champion adaptation** is a three-stage workflow in the advanced Models tab. Stage A adds fresh local transitions to saved replay by executing the champion policy with sparse, small action perturbations; actor, critic, and entropy parameters do not update, and the expanded candidate must pass paired seeded laps against the source champion. Stage B trains only the critic and target critic, leaving actor weights and entropy fixed, then stores a validated candidate separately from the champion. Stage C runs a second seeded closed-loop comparison against the tuned source champion and only then promotes the candidate atomically with a full backup. These comparisons use paired lap deltas from the same seeded evaluation, completion and failure rates, position/progress/heading drift, and action disagreement. A rejected candidate leaves the source champion active and the last complete working checkpoint available. The candidate checkpoint and source policy/overlay digest are stored together, so an interrupted write cannot attach stale lineage to new replay. **Run full cycle** runs all three stages; **Validate & promote candidate** resumes Stage C if needed. Speed-search and overlay-search promotions mark tuned checkpoints as requiring adaptation, and ordinary TQC continuation refuses them until Stage C passes. Actor-gradient polishing remains a separate experimental action with its own rollback. TQC keeps independent actor and critic learning rates when configured. Use **Load tuned champion adaptation preset** before running the Summer 1 workflow so the rates and conservative replay-noise settings match the validated profile.

```text
models/<track>/<algorithm>/
  latest/policy.zip, metadata.json, replay.pkl (DQN or TQC)
  champion/policy.zip, metadata.json
  checkpoints/step-<N>/policy.zip, metadata.json, replay.pkl (DQN or TQC)
```

Metadata includes the app version and v2 schema versions, architecture, parameter counts, observation and action schemas, track, reward profile, curriculum, complete configuration, training steps, physics ticks, elapsed wall time, seed, device, finish/crash totals, evaluation, and Git commit. Resume requires compatible track, action and observation schemas, architecture, and rewards. Old PPO checkpoints with discrete PWM actions are explicitly rejected; PPO now uses continuous `Box(2)` actions and must be initialized fresh or distilled from a compatible TQC teacher. New DQN/TQC champions save their replay buffers alongside policy weights. Older champions without replay can continue from their policy weights using a fresh replay buffer; the policy refills it before gradient updates resume. No v1 model is loadable through this path.

## Observation and protocol

All three algorithms receive the same normalized `polybot.observation.v2` vector: 45 state features followed by four values and one validity mask for each lookahead point (`45 + 5N`, so 105 values at N=12). State order is local velocity (3), acceleration (3), angular velocity (3), up vector (3), route progress, lateral and heading errors, pitch, roll, wheel contacts (4), suspension lengths (4), suspension velocities (4), wheel skids (4), actual steering, ghost relative position (3), ghost heading, ghost target speed, ghost action (3), and previous digital action (3). Lookahead points contain forward, right, up and curvature values. See `Telemetry.to_vector()` for the exact scaling and clipping. No algorithm-specific observation slice is masked.

The simulator protocol remains `polybot.sim` version 2. The wire action is always digital steering {-1,0,1} and binary throttle/brake. The mock implements the same handshake/reset/step contract as the PolyModLoader adapter. See [protocol](protocol.md).

## Devices and diagnosis

`device=auto` prefers CPU for PPO's small MLP updates and uses CUDA for DQN/TQC if PyTorch can initialize it. The selection reason is logged. Explicit `cuda` fails when unavailable and overrides PPO's CPU preference. `polybot-doctor` reports PyTorch version, CUDA build, availability, GPU count/name, and NVIDIA driver visibility. `polybot-doctor --smoke ppo|dqn|tqc` builds a tiny policy; the DQN smoke also trains, saves, and reloads replay. Small DQN networks may run faster on CPU than CUDA because GPU launch overhead can dominate.

For a fresh run, start with Balanced rewards, compact architecture, 2–4 TQC train frequency on modest hardware, and an evaluation interval long enough to avoid spending most of the run on testing. The GUI warns about unusual combinations but never silently changes them. For all exact meanings, hover over a field; the descriptions come from `training/parameters.py` and are checked by tests.

The same central help is available without the GUI through `polybot-train --parameter-help`.
